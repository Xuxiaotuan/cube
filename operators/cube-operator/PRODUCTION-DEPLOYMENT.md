# Production deployment and disaster recovery prerequisites

Scope: Router process HA plus file-import preaggregation recovery. This is a review/runbook, not an executable deployment or certification. No live mutations or destructive recovery commands are included. The current reported local environment is one OrbStack node, so node-failure, permanent-volume-loss and production topology acceptance remain `external_blocked`. Obtain actual topology, storage provider, approved RPO and RTO from the owner before planning production changes.

## Current contracts and configuration

- `CubeCluster.spec.metaStore.replicas` must remain 1. Its StatefulSet PVC is `ReadWriteOnce`; RWO does not fence two processes on the same node and does not prove safe detach after partition. Never run two RocksDB writers, increase replicas, force-delete the old Pod or force-attach a volume without independent old-node/storage fencing.
- Router default anti-affinity is preferred, not required. Production configuration must use supported `router.pod.affinity` required anti-affinity or `topologySpreadConstraints` with `DoNotSchedule` and verified failure-domain labels. Prove actual Router Pods are on separate nodes and, where required, zones. Do not invent available nodes/zones or treat Pending Pods as protected availability.
- Use `storage.storageClassName`, `dataSize`, and same-namespace `objectStoreSecretRef` as defined in the existing CRD. StorageClass/template transitions are blocked by the controller and need an approved migration. Validate provider detach/reattach, durability, topology and backup semantics independently. A singleton PDB intentionally blocks routine drain; do not bypass it casually.
- `config/rbac/{service_account,role,role_binding}.yaml` now agrees with `config/manager/manager.yaml`: namespace `cube-operator-demo`, ServiceAccount `cube-operator`, namespaced Lease permissions. These are aligned example defaults, not the actual production namespace. Render ALL references consistently to the chosen namespace; do not apply these examples to the running remediation environment. Manager leader-election namespace must match this namespace as configured by the actual Manager binary. `WATCH_NAMESPACE` alone does not prove leader-election namespace selection. The parent owns Manager startup/flags and live authorization checks.
- Independently check Manager SA can get/list/watch/create/update/patch Leases in the chosen election namespace, Router agent can only read required authoritative state, and all Operator replicas share a single election identity. Keep release operator digest and lease-agent digest separately pinned. Manager leadership is not storage fencing.
- Runtime defaults use `/livez`, `/readyz` on Rust 3030; HA API/Refresher process liveness uses `/livez/process` on 4000. Prove those endpoints in the pinned images. Startup failure threshold is 60 at a 5-second period; this is a startup allowance, not measured recovery time. Avoid restart storms caused by dependency-based liveness during Router failover.
- The CR supports `router.drainCommand` and `router.pod.terminationGracePeriodSeconds`. Use only a command actually supported by the pinned image; the existing example mentions `/cube/cubestored --drain`, but invocation is not certified here. With drain configured the controller requires explicit grace >=40 seconds if supplied. Exercise removal from Leader Service, rejected new mutations, drain completion and SIGTERM timing; choose grace from observed worst case. API/Worker/MetaStore also support per-role grace/probe configuration.
- Keep readiness/admin/RPC/metrics and object-store endpoints private. Adopt namespace/CNI-specific ingress rules after inventorying Operator-to-Pod probes, Router/Worker-to-MetaStore RPC, DNS, API server and object-store traffic. Do not publish a blanket NetworkPolicy that accidentally breaks fencing observations. Secret encryption, transport authentication and external API routing remain deployment-owner responsibilities.

## Operator metrics and evidence boundaries

`cube_cluster_condition{namespace,cluster,condition}` reports 1=True, 0=False, -1=Unknown/stale generation for a bounded set of conditions. `cube_cluster_observation_timestamp_seconds` is the last full successful status observation. Check its freshness; a retained 1 during control-plane loss is not current proof. Metrics are cleared when the CR is observed deleted. Upgrade/invalid-state observations do not refresh the full-observation timestamp. Prometheus registry export/server wiring and scraping must be checked against the parent-owned Manager binary.

Suggested alerts: stale full observations, UpgradeReady=0, serving readiness absent/false, UNKNOWN recovery and ProductionReady!=1 for any environment claiming certification. Keep recovery conditions distinct. Do not label metrics by buildId/tableId/epoch; retain detailed correlation in logs/evidence. These metrics do not implement missing build backlog, UNKNOWN age, recovery-record bytes, PVC capacity or per-stage Router failover latency. Obtain actual app/storage metrics and tests in their owning scopes; use kubelet volume bytes only where the provider exports them. Do not interpret reconciliation duration as outage or business recovery latency.

## Disaster recovery: approval before action

Record incident owner, cluster namespace/name/UID, child Router UID, authoritative Lease and role-state marker identities/epoch/resourceVersion, frozen release ID, storage identities, object-store prefix, agreed RPO/RTO and observation start time. Preserve snapshots/raw evidence with access controls; do not log credentials. A Lease missing after prior initialization is not permission to delete its marker or restart epoch=1.

1. **Quiesce and fence.** Obtain explicit maintenance approval and loss/rollback bounds. Stop new external work and refresh scheduling using the supported operations owned by the incident operator. Do not mistake lack of API connectivity for a dead process. Fence the old node/process at an independent infrastructure/storage boundary and record confirmation from the provider. Verify old Router/Worker/Refresher identities cannot commit to MetaStore or publish objects. If fencing cannot be proven, stop: `external_blocked`.
2. **Capture a consistent recovery set.** Preserve MetaStore metadata/Job attempts/table identities, CacheStore protected build records and immutable manifests (including UNKNOWN), and all referenced object files/version IDs/checksums. Establish where CacheStore is persisted in the exact release and capture its durable storage, not just generic cache keys. With all writers quiesced, use provider/application-supported consistent snapshots/backups. A live directory copy of RocksDB or metadata-only snapshot is not a demonstrated backup. Record consistency barrier/time and which writes are excluded from the RPO.
3. **Validate backup before restore.** Preserve the original media/snapshots and object versions. Create an isolated target with no business traffic and no shared writable directory. Verify backup integrity, exact release readability, credentials and object inventory. Missing build manifests/objects or inconsistent epochs are a blocker, not a reason to discard UNKNOWN records. No broad object-prefix cleanup/TTL is allowed during recovery.
4. **Restore single writer.** Only after old-node fencing is independently confirmed, follow the storage provider's detach/reattach or replacement-volume procedure. Restore MetaStore, CacheStore and objects from the same consistency set. Start exactly one MetaStore writer with compatible binaries; retain authority epoch/history and use the separately reviewed controlled Lease recovery procedure if needed. Do not lower epoch, delete safety markers, or create a second RocksDB process to regain availability.
5. **Reconcile before serving.** Compare restored metadata tables to object versions/checksums; compare CacheStore buildId/manifests/target tableId and phase records to physical tables and Job attempt ownership. Reconcile unpublished uploads, ready-but-unconfirmed tables, active and UNKNOWN builds using supported recovery logic. Verify old executors still cannot commit after replacement starts. Test late/retried requests and ensure one visible publication, not merely a successful HTTP response.
6. **Measure and reopen.** Query fixed data and expected counts/checksums, finish an interrupted build with original identity, and observe sustained queries/refreshing. Measure old-write rejection, service recovery, query recovery and build completion separately. Compare actual data loss and restoration duration against approved RPO/RTO. Reopen traffic only with owner approval and archived same-release evidence. Failed consistency checks keep the target isolated and original backups intact.

Permanent disk loss, cross-node reattachment and backup restore are separate exercises. A successful Pod deletion on OrbStack proves none of them. For each drill archive the provider fencing evidence, backup inventory/checksums, restoration actions, query results, identity/publication assertions and measured times using `RELEASE-ACCEPTANCE.md`. Rollback after new protocol writes needs reverse-compatibility proof or restore of the complete consistent recovery set, never just replacement with an older image.
